# Routing reference

Choose the narrowest durable destination that makes future correct behavior automatic or easy to discover.

| Lesson type | Preferred final form | Neutral example |
| --- | --- | --- |
| A mistake can be detected automatically | Test, static rule, type/schema rule, CI, script guard | Unsupported internal entrypoints are blocked structurally or by a check |
| A surprising implementation must remain | Local `WHY` explanation | Explain why an apparently redundant normalization step is required |
| Consumers need usage/setup knowledge | Package README / developer docs | Required initialization order for a subsystem |
| A design decision and tradeoff must survive | ADR / architecture docs | A boundary between pure logic and persistence is intentional |
| Rule applies only inside one subtree | Scoped agent instructions | Generated files in one subtree must not be edited manually |
| Repeatable reasoning/procedure, loaded on demand | Skill | Diagnose a recurring class of integration-test failures |
| Repeated deterministic operation | Command/script | Reset an isolated test environment safely |
| Task needs dedicated bounded role/tool context | Specialized agent | Release-focused agent with deployment-only context |
| Short rule applies broadly to relevant sessions | Root agent instructions | Use the repository's declared package/tool manager |
| Temporary unresolved deficiency | Friction / issue tracker | Resource cleanup in a test harness is unreliable |
| No longer true or useful | Delete | Workaround for behavior no longer present |

## Promotion examples

### Narrative to enforcement

Inbox lesson:

> Contributors repeatedly used an unsupported internal API because the public boundary was not mechanically clear.

Best outcome:

1. Restrict the public surface structurally.
2. Add an automated guard if needed.
3. Document supported usage only where consumers need it.
4. Delete the lesson.

Do **not** add a permanent root rule if repository structure already enforces the boundary.

### Narrative to code-local explanation

Inbox lesson:

> Removing an apparently redundant conversion changes observable behavior because an upstream boundary uses a different unit/representation.

Best outcome:

Add a short `WHY` explanation beside the conversion and a regression test when feasible. Delete the lesson.

### Narrative to skill

Inbox lesson:

> Diagnosing a recurring integration failure requires acquiring isolated resources, starting services in a specific order, collecting traces, and checking several known failure classes.

Best outcome:

Create or update a focused diagnostic skill. Keep commands/scripts as executable helpers. Add only a small discovery pointer to always-on instructions when needed. Delete the lesson.

### Narrative to scoped agent rule

Inbox lesson:

> Files generated by a tool must not be hand-edited and changes in the source contract must refresh generated outputs.

Best outcome:

Enforce generation checks where possible and put any remaining concise instruction at the smallest applicable scope. Delete the lesson.

## Anti-patterns

- Appending every lesson to root agent instructions.
- Keeping the lesson inbox as permanent historical memory after promotion.
- Duplicating the same rule in documentation, agent instructions, a skill, and code comments.
- Encoding a transient bug workaround as an architectural principle.
- Creating a skill for a one-line invariant.
- Creating a command for something CI should simply automate.
- Preserving a lesson only because it was difficult to discover even though it is no longer true.
- Adding repository-specific content to this shared skill.
